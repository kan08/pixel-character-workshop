Muse に言葉か画像を渡し、基準画を決めてから 2D アニメーションを作る。Muse が基準画 PNG、動く GIF、前版比較を対象版に固定して届ける。人は Muse の会話を窓口に実物を確認し、修正や採用を返す。

人の窓口は Muse

依頼から採用まで同じ会話で進む。GitHub は Muse と制作側が使う共有メモリ。

ゴールは動く 2D アニメ

基準画はキャラの顔や服を保って動かすための Step 1。繰り返す詰まりは発生した工程の検査や道具に還元する。

PowerAI とは独立運用

窓口・共有メモリ・改善の型を借りる。2D アニメ制作は専用リポジトリ、専用の配信・起動設定で回す。

言葉だけでも、元絵を渡しても始められる

右向きの歩きアニメを作る例。言葉から基準画を生成する場合も、画像を持ち込む場合も、アニメ制作に使う基準画の版を Muse で確定する。

基準画が届いたら

Muse が「基準画 v1 が見られます」と PNG のリンクを返す。「髪の色を変えて」で次版へ。「これで採用。次は右向きの歩きにして」で、採用した PNG を使うアニメ依頼へ進む。

「左足が滑る。顔はそのまま」

Muse は v1 を修正元として固定し、変更点と残す点を v2 の依頼に記録する。v2 には v1 との比較リンクを添える。

「これで採用」

採用は人が見た版に結び付けて記録する。返事がどの版を指すか曖昧なときは、Muse が対象版だけを確かめる。

「また足がズレた」

今回の修正と並行して、対象版と再現条件を工程タグ付きで改善記録に残す。

エンジンを替えても、依頼と結果の形は共通

Mac 上の受け渡し役が、裏側の GitHub にある依頼を1版分の作業フォルダに用意する。言葉だけなら job.json を置き、元絵や前版があれば参照パスと素材を加える。各ツール向けの変換と書き出しは接続処理が担当する。

アニメを修正する版のフォルダ例

jobs/walk-017/v2/
  job.json
  input/character.png
  input/previous.gif
  result.json
  output/walk.gif
  output/frames.png
  output/frames.json

言葉だけの依頼は画像なしで渡す

Step 1 の作業フォルダに置く入力は job.json だけ。基準画 PNG を採用したら、その版を参照してアニメ制作へ進み、GIF とスプライトシート PNG・フレーム情報 JSON を出す。

JSON の例

Phase 0 用の提案。依頼 ID は制作 Issue からたどれる識別子、版は同じ依頼の中で増える番号。基準画を採用してアニメ化へ進むときは、採用した PNG を参照する別の依頼を起票する。

A　job.json ／ 言葉だけで基準画を作る

{
  "jobId": "character-016",
  "revision": 1,
  "baseRevision": null,
  "kind": "illustration",
  "request": "緑の雨合羽のキャラで右向きの歩きアニメ。まず基準画から",
  "inputs": {}
}

B　job.json ／ 元絵を使って歩きの前版を直す

{
  "jobId": "walk-017",
  "revision": 2,
  "baseRevision": 1,
  "kind": "animation",
  "request": "左足が滑る。顔はそのまま",
  "change": "左足の接地を直す",
  "keep": "顔と右向きの歩き",
  "inputs": {
    "reference": "input/character.png",
    "previous": "input/previous.gif"
  }
}

result.json ／ B の依頼にエンジンが返す結果

{
  "jobId": "walk-017",
  "revision": 2,
  "artifacts": ["output/walk.gif", "output/frames.png", "output/frames.json"],
  "preview": "output/walk.gif",
  "checks": [
    {"name": "gif-decode", "status": "pass"},
    {"name": "frame-count", "status": "pass"},
    {"name": "loop-seam", "status": "pass"},
    {"name": "sheet-layout", "status": "pass"},
    {"name": "sheet-json", "status": "pass"}
  ]
}

kind は illustration、pixel、animation のいずれか。初版は baseRevision を null にする。inputs に、元絵があれば reference、前版があれば previous を書く。どちらもないときは inputs を空にするか省略する。パスは作業フォルダ内の相対パス。実行前に入力の版を固定し、結果の ID・版の一致、出力の存在、用途ごとの必須検査を確かめてから版を保存する。検査結果は pass、fail、skipped で表す。

誰が何を記録するか

Muse
依頼の原文と、指定があれば元絵・変える点・残す点を起票する。結果や要確認点を知らせ、人の修正指示と採用した版を記録する。
独立 GitHub
制作 Issue が依頼と進行状態・採用履歴の正本。版フォルダは入出力の記録。改善記録は制作 Issue や該当版を参照する。
制作エンジン
版ごとの入力を読み、生成・修正・検品・書き出しを行う。接続処理がツールの違いを吸収する。
プレビュー配信
対象版に固定した閲覧 URL を返す。受け渡し役が Issue に URL を記録し、Muse はその版とリンクを取得する。
改善サイクル
工程タグ、再現条件、変更効果を記録し、採用した検査・道具・手順を該当工程の次の制作に反映する。

状態の提案　受付 → 制作中 → 確認待ち → 採用。修正は次版を受付に戻す。生成や配信が止まった場合は、止まった箇所・理由・再開先を Issue に残す。確認待ちにする条件は、成果物の保存と対象版の閲覧経路の確認がそろうこと。

レイヤー2　制作の5ステップと工程別改善

基準画で姿を決め、キーポーズで動きを設計し、全コマを揃えてから書き出す。Muse で動く実物を見て違和感があれば、原因の工程だけを修正し、その出力を使って後続工程を更新する。

手戻りは原因に当たる工程から

顔や服の違いが基準画にあれば Step 1、一部のコマに限られるなら Step 3。足踏みや体重移動は Step 2、1コマの崩れや小物落ちは Step 3。テンポや足元の滑りは Step 4 の表示時間・基準点・書き出し設定を直す。

再発は工程タグ付きで記録する

検品失敗や差し戻しから、対象版、発生工程、原文、期待する状態と再現素材を残す。原因に応じて step1〜step4 を付ける。Step 5 で気づいた症状も、原因の工程に結び付ける。

検査や道具で防げる箇所から改修

切り抜き、位置揃え、パレット統一、GIF のコマ数などは、検査やスクリプトを先に直す。顔やポーズが安定しない場合は、参照画像の渡し方、ポーズガイド、プロンプトを調整する。同じ素材で改修前後を比較し、副作用も確かめてから該当工程の標準に反映する。

各工程の処理と検品

工程主な処理自動検品人間確認改善還元先
Step 1
基準画		 主な処理言葉から生成、または持ち込み画像を解像度・透過・向き・床ライン・足元基準点で正規化。 自動検品解像度、透過、キャラの欠け、背景ゴミ。 人間確認関門①。Muse で顔・服・雰囲気を確認し、基準画の版を確定。 改善還元先step1　正規化・切り抜きスクリプト、基準画の生成プロンプト。

Muse だけで完結する4つの約束

人の操作は Muse の会話と、会話から直接開けるプレビューで完結する。記録や制作側との受け渡しは Muse と運用側が担う。

① 言葉でも画像付きでも受付
キャラと元絵の有無、作りたい動作、変える点、残す点を Muse が短く確認する。合意したら、原文を添えて制作依頼を記録する。
② 対象版を会話で連絡
新たに確認待ちとなった版を、対象と版を明記して知らせる。基準画 PNG・動く GIF・前版比較は、版固定 URL か直接表示で届ける。変更点、検品結果、見てほしい点、返し方も添える。
③ 見ている版に返事を結ぶ
修正指示は原文と変える点・残す点を見た版に結び付け、次版を起票する。採用は見た版を固定する。採用した基準画はアニメ制作の参照に使う。版が曖昧なら対象版だけを確認する。
④ 詰まりを同時に記録
再発の指摘や、同じ版で検品失敗・差し戻しが2回以上起きたときは、今回の制作を進めながら対象版・工程タグ・原文・期待する状態を改善記録に残す。

Phase 0 の案　Muse から版ごとの静的ページを開く

公開可能な試験用の PNG と GIF で往復を試す。非公開素材は認証付きの閲覧ページか、共有範囲を確認した Muse 添付で届ける。静的配信では、配信する各ホストのページ URL と画像 URL を、許可済み端末と未ログイン端末で確認する。

Phase 0 の完了条件

スマホで Muse の通知から基準画 PNG を開いて確定し、動く GIF を再生する。「テンポを遅くして」で Step 4 を更新し、Muse から届く次版と前版を比較して採用を返す。運用側は、実際の詰まり1件を工程タグ付きで記録・改修し、同じ素材で前後を確かめる。

Phase 1 の完了条件

実生成エンジンをつなぎ、言葉だけの依頼と元絵の持ち込みからそれぞれアニメ制作を試す。同じ形式で結果を保存し、Muse が対象版を届ける。

Phase 2 の完了条件

壊れた出力は制作側で止まり、人に見せるものは検品結果と版が追える。改善前後を同じ条件で比較し、別素材で副作用を確かめる。手戻り回数や初回の閲覧までの時間は、記録できた実績を使う。

最初の改善候補　1コマで止まる GIF を検知する

たとえば動くはずの GIF が静止したら、step4 と書き出し条件を記録する。完成ファイルのコマ数を調べる検査を加え、失敗素材が止まり、正常素材が通ることを確かめる。Phase 0 では実際に起きた詰まりを選ぶ。

最初に決める7つの論点

各項目の「初案」は Phase 0 を通すための提案。Muse の実接続、スマホでの添付再生、非公開プレビューの挙動は実環境での確認が必要。

1. Mac 側の起動

初案は手動起動。運用側が Muse から受け付けた依頼を指定し、基準画 PNG と動く GIF の試験版を登録する。人への連絡は Muse が行う。制作側の起動を自動化する段階で、ポーリングか Webhook を選ぶ。

ポーリングは受信口を設けずに始めやすいが、Mac の停止や巡回間隔で待ちが出る。Webhook は早く動き出せる一方、到達できる受信口と再送時の重複対策が要る。

2. プレビューの公開範囲

初案は公開可能な試験用 PNG・GIF を Muse から案内。非公開素材は認証付きの版固定ページか、共有範囲を確認した Muse 添付で届ける。期限付きリンクを使う場合は、転送できる素材の範囲と期限切れ後の案内を決める。

配信には閲覧用の成果物だけを渡す。持ち込んだ元絵を外部生成先へ渡せる範囲、過去版の保持、公開停止の担当も決める。

3. 版の修正と工程改善

初案は次版の修正と工程別の改善記録を並行。基準画の「髪の色を変えて」や歩きの「左足を直して」は、見た版に紐付けて次版へ。「また同じ条件で足がズレた」は原因の工程タグ付きで改善記録にも残す。受け渡しを止める詰まりは、1回でも改善候補にできる。

検査や変換で防げる問題から直す。絵柄やポーズの問題は参考例やプロンプトを調整し、いずれも同じ再現素材で前後を比較する。

4. 差し替えの入出力

初案は1版1フォルダと2つの JSON。テキストのみの新規生成と、画像を参照する修正・アニメ化を共通の入出力で扱う。手動で素材を返す段階から実生成をつないだ後まで、同じ形式で結果が戻るかを試す。対応できない用途は理由付きで返す。

用途ごとの追加情報が必要になったら任意フィールドから始める。互換性を壊す変更が必要になった段階で契約の版番号を導入する。

5. 自動検品と人の目

初案はファイルの破損と明示仕様を自動検査。基準画では指定サイズや透過、GIF ではコマ数やループの継ぎ目などを調べる。判定しきい値は実例で検出漏れと過検出を確かめて決める。

人は関門①で基準画の姿を確定する。関門②では出荷ゲート通過後の GIF を Muse から見て、自然さや動きの気持ちよさを最終判定する。

6. PowerAI との距離

運用は別リポジトリ・別設定。Muse が両方を扱う場合も、2D アニメの依頼は専用リポジトリへ送る。配信・起動・ワーカーの設定も制作側で持つ。

ゲーム用ラベル、3レーン、Playtester、自動マージはゲーム開発側の運用。PowerAI の停止中も、Muse からアニメ制作と版固定のプレビューを試せる構成にする。

7. 再送・失敗・採用の整合

初案は依頼ごとに制作中の版を1つにし、依頼 ID と版の組で重複実行を防ぐ。処理と配信が別々に失敗する場合に備え、保存済み成果があれば配信から再開する。試行を打ち切る回数・費用は実生成をつなぐ際に決める。

通知と採用は人が見た版にひも付ける。アニメ化へ進むときは採用した PNG の版を入力に固定する。同時修正や複数候補を扱う段階では、版の発行と競合時の扱いを先に決める。
